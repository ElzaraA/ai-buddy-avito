# Вопросы жюри и короткие ответы

Каждый ответ ссылается на код или тест, чтобы его можно было проверить.

## Что если LLM соврёт?
Инвариант 1 из `specs/agent/spec.md`: нет найденного фрагмента базы — нет ответа. Текстовый ответ
модели без источника агент превращает в отказ с именем наставника, даже если модель «знает» ответ.
Тест: `internal/agent/llm_contract_test.go: TestLLMOutputs`, случай `hallucination without sources`.
Там же проверяются ответы не в JSON, неизвестный инструмент и мусорные даты.

## Как защищены права?
- Каждый инструмент сам вызывает `auth.Can` (`internal/tools/*.go`); агент проверяет право ещё при
  подготовке черновика (`internal/agent/agent.go`), API — при подтверждении и согласовании
  (`internal/api/actions.go`).
- Владелец проверяется для заявок, шагов чек-листа и диалогов: чужое — `403`
  (`TestChatForeignSessionForbidden`, `TestProgressAndSteps`).
- Согласовать может только руководитель своей команды; стажёр сам себе не согласует.
- База знаний работает по принципу deny-by-default: фрагмент без `audience` не виден никому,
  фрагмент чужой команды не виден (`internal/rag/index.go`).
- MCP берёт пользователя из контекста запроса, а не из аргументов инструмента (`internal/api/mcp.go`).

## Может ли агент сам оформить отгул?
Нет. Даже если модель вернула вызов мутирующего инструмента (в чате или через MCP), получается только
черновик; заявка появляется после «Отправить» у стажёра, а отгул согласует руководитель.
Тест: `internal/agent/llm_contract_test.go: TestToolCallDoesNotMutate`; 30 параллельных подтверждений
одной заявки дают ровно одно успешное — `internal/api/actions_api_test.go: TestConfirmConcurrent`.

## Почему BM25, а не эмбеддинги?
База стажёра маленькая и терминологическая (GitLab, Grafana, код-ревью): точное совпадение слов
работает надёжно, не требует внешней модели и даёт детерминированный результат для тестов.
Порог релевантности (`minScore` в `internal/rag/index.go`) отсекает случайные совпадения, поэтому
вопрос не по базе уходит в честный отказ. Эмбеддинги поверх BM25 — в roadmap.

## Почему в демо mock-LLM?
Демо и CI должны работать без ключа и интернета, а ответы — повторяться, чтобы golden-набор
(`data/golden/golden.json`) и сценарии проверялись автоматически. Все инварианты (источник, права,
черновик) живут в коде агента, а не в модели, поэтому на реальной модели они те же.

## Как подключить реальную модель?
В `.env`: `LLM_MOCK=false`, `LLM_API_KEY=...`, при необходимости `LLM_BASE_URL` и `LLM_MODEL`
(любой OpenAI-совместимый `/chat/completions`, в Авито — модель во внутреннем контуре).
При сбое основной модели клиент повторяет запрос, затем отвечает резервная модель, а ответ
помечается `"degraded": true` (отключается `LLM_FALLBACK=false`). Переходы считает метрика
`buddy_llm_fallback_total`.

## LLM не блокирует интерфейс?
Сообщение в чат возвращает `202` сразу, ответ приходит по SSE. Таймауты: весь прогон агента 60 с,
вызов инструмента 10 с (`internal/tools/registry.go`). Нагрузка: 100 параллельных диалогов без потерь —
`internal/api/resilience_test.go: TestHundredParallelChats`.

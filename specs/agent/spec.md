# Agent Spec — AI-buddy

## Роль
AI-buddy — помощник стажёра Авито (в демо — команды Backend и Frontend). Отвечает по базе знаний со ссылкой на источник, готовит действия через инструменты корпоративных сервисов (имитации) и ведёт по чек-листу.

## Инварианты (каждый закреплён тестом — см. `specs/traceability.md`)
1. **Нет источника — нет ответа.** Текстовый ответ без найденного фрагмента базы превращается в отказ с именем наставника — даже если LLM «знает» ответ.
2. **Нет права — нет действия.** Каждый инструмент проверяет `auth.Can` до выполнения; подтверждение действия проверяет право роли и владельца.
3. **Deny-by-default по аудитории.** Фрагмент без `audience` не виден никому; фрагмент чужой команды не виден.
4. **Draft → Confirm.** Агент не выполняет мутирующие инструменты (`absence_create_request`, `access_request`) — даже если LLM вернула `tool_call`, получается только черновик. Действие создаётся после `POST /actions/{id}/confirm`, атомарно (двойное подтверждение — 409).
5. **LLM не блокирует UI.** `POST /messages` → 202 за миллисекунды, ответ — по SSE.
6. **Таймауты:** run 60 с, инструмент 10 с, HTTP-клиент LLM 20 с (`internal/api/app.go`). Сбой LLM → событие `error` с понятным текстом, внутренние детали наружу не уходят.
7. **Инструкции в вопросе не меняют правил.** Prompt injection максимум создаёт черновик, который пользователь сам подтверждает или отменяет.

8. **Сбой LLM не останавливает сервис.** Временные ошибки (сеть, 429, 5xx) повторяются с паузой; если модель недоступна, отвечает резервная детерминированная модель, ответ помечается `degraded: true`.
9. **MCP = те же гарантии.** Внешний агент через `POST /mcp` получает те же инструменты: пользователь из контекста, право до вызова, мутации — только черновик.
10. **Заявку согласует руководитель своей команды.** Не сам автор, не наставник, не другая команда; решение окончательное и записывается в историю заявки.

## Жизненный цикл действия
```
draft ──confirm (владелец, право роли)──► pending ──approve (руководитель команды)──► approved
  │                                          ├──────reject  (руководитель команды)──► rejected
  └──────────cancel (владелец)───────────────┴──────cancel  (владелец)─────────────► cancelled
```
Для заявки на доступ статус двигает шаг чек-листа вида `access`: pending → шаг `waiting` (с `related_action_id`), approved → `done`, rejected/cancelled → снова `todo`.

## Поток обработки сообщения
```
вопрос ─► RAG (BM25 + префикс 5 рун, стоп-слова, фильтр team/audience, порог score и покрытия запроса)
       ─► LLM (mock | OpenAI-совместимая, JSON-ответ)
       ─► answer   → есть источники? ответ + sources : отказ
          tool_call→ мутирующий? черновик : проверка права → выполнение → action
          draft    → черновик (absence | access), сохраняется со статусом draft и action_id
          refusal  → отказ + buddy_name
```

## Формат ответа LLM
```json
{"type":"answer","text":"..."}
{"type":"tool_call","tool":"checklist_get","args":{}}
{"type":"refusal","text":"..."}
```
Ответ агента клиенту — `AgentResponse` из `specs/contracts/openapi.yaml`.

## Инструменты
| Имя | Право | Подтверждение | Результат |
|---|---|---|---|
| checklist_get | checklist.read | нет | items, next_step |
| absence_get_policy | checklist.read | нет | policy, manager_name, buddy_name |
| absence_create_request | absence.create | **да** | черновик ABS-…, после confirm — pending |
| access_request | access.request | **да** | черновик REQ-…, после confirm — pending |
| directory_find_owner | directory.read | нет | owner |

Схемы — `specs/contracts/mcp-tools.json`, промпт со списком инструментов — `internal/agent/prompts.go`.

## Диалог
Модели передаются последние 6 реплик диалога (`AskWithHistory`). Одновременно в одном диалоге ждут ответа не более 3 вопросов (дальше 429).
Уточнение даты отгула: если помощник спросил дату, а пользователь ответил только датой («2026-11-20», «в пятницу», «завтра»), сообщение продолжает сценарий отгула (`withDialogContext` в `internal/api/chat.go`).

## RAG
- Источник: `data/knowledge/*.md`, чанкинг по заголовкам, метаданные `stage`, `team`, `audience` в HTML-комментарии.
- Заголовок раздела индексируется вместе с текстом.
- Стоп-слова и числа не участвуют в поиске; фрагмент релевантен, если score ≥ 0.5, в коротком запросе (≤ 2 значимых слов) совпали все слова, а в длинном — ≥ 60% веса запроса (сумма IDF).
- Совпадение слов строгое: точное, по общей основе или по префиксу, если «хвост» основы не длиннее 3 букв (`termMatch`). Раньше хватало пяти общих букв, и «командировку» находила «команду» → фрагмент про Jira.
- Кадровые темы вне базы (командировка, ДМС, страховка, отпуск по уходу/декрет, парковка, переезд, спортзал, столовая, компенсации): если фрагмента нет — честный отказ «Не нашёл ответа…» без вызова модели (`outOfScope`), а не подмена политикой отгулов. Золотые кейсы `OT-*` в `data/golden/golden.json`.

## Асинхронность
`POST /chat/sessions` → 201; `POST /chat/sessions/{id}/messages` → 202; `GET /chat/sessions/{id}/events` (SSE): `status` → `tool_result` → `message_done`. Подписка регистрируется до отправки заголовков; готовые ответы повторяются при подключении; heartbeat каждые 15 с.

## Кабинет наставника и руководителя
`/team/progress`, `/team/actions`, `/team/knowledge-gaps`, `/team/summary` — только своя команда и только роли buddy/lead.
«Пробелы базы знаний»: каждый отказ из-за отсутствия источника запоминается без автора, а персональные данные в тексте вопроса (e-mail, телефон и т. п.) маскируются до сохранения; наставник видит, какие инструкции дописать.
Контакты в ответах (`buddy_name`, `manager_name` — отказ, правила отгула) берутся по команде пользователя: стажёр frontend видит наставника и руководителя своей команды, а не backend.

### Сигналы наставнику (двусторонняя петля)
- «Передай наставнику: …» сохраняет именной сигнал (`SIG-…`, topic blocked|tech|unclear|other, PII маскируются, ≤ 500 символов). Наставник видит их в `GET /team/signals` (открытые сверху).
- `POST /team/signals/{id}/resolve` — тело необязательно: `{"reply": "..."}` (≤ 500 символов, PII маскируются, иначе 400). Сигнал получает `done`, `reply`, `resolved_by` (имя наставника), `resolved_at`. Пустой reply не затирает прежний.
- Стажёр видит свои сигналы и ответы в `GET /signals/me` (новые сверху; не стажёру — 403). Всё сохраняется в снимке `STATE_FILE`.

### «Пульс»
Стажёр раз в день отмечает самочувствие 1..5 и заметку ≤ 300 символов (`POST /pulse`, повтор за день перезаписывает). «Сегодня» — по поясу `TZ_NAME` (по умолчанию Europe/Moscow; без tzdata — фиксированный UTC+3; tzdata встроена в бинарник). `GET /team/pulse` — риск: сегодня ≤ 2, или 2 из 3 последних ≤ 2, или среднее за 7 дней ≤ 2.5; заметка видна только наставнику и руководителю команды.

### Достижения
`GET /achievements` (только стажёр) — 7 достижений, выводятся из состояния (вопросы, заявки, сигналы, серия «Пульса», шаги чек-листа), отдельно не хранятся.

### Честное «Сэкономлено наставнику» (`/team/summary`)
`questions_closed = kb_answers + glossary_answers + confirmed_actions`: ответ по базе знаний с источником, объяснение термина из словаря, заявка, подтверждённая стажёром (считается при `confirm`, не при черновике; отмена после подтверждения списывает). Меню, small talk, просмотр чек-листа, черновики и отмены не считаются; отказы и сигналы считаются отдельно (`refusals_total`, `signals_total`). `mentor_minutes_saved = questions_closed × 5`.

### Подсказки (suggestions)
Подсказка «Передай наставнику: <вопрос>» не предлагается, если вопрос — prompt injection, о зарплате или содержит персональные данные; после отказа про зарплату — «Кому написать про условия стажировки?» (отвечает: HR BP или руководитель). «Запроси доступ в X» не предлагается, если заявка на X уже отправлена или одобрена (`Agent.AccessStatus`), вместо неё — ещё не запрошенная система.

### Шаг «Получить доступы (Git, Jira, Grafana)»
Закрывается, только когда одобрены все три системы (Git ≡ GitLab). Пока нет — `status: todo` с `sub_done`/`sub_total`/`missing`, а `how_to` следующего шага называет недостающие системы; всё запрошено и ждёт решения — `waiting`. Вручную шаг не закрывается (409).

### Демо-режим
`GET /demo` → `{"demo_mode", "llm": "mock"|"real"}`. `POST /demo/reset` (только `DEMO_MODE=true`, иначе 404; любой демо-пользователь; под лимитом записи) сбрасывает всё состояние в памяти — заявки, чек-листы (засеваются заново), сигналы, «Пульс», пробелы, счётчики пользы и достижений, диалоги — как при свежем старте.

## Наблюдаемость и защита
- `/metrics` (Prometheus): HTTP по шаблону маршрута, ответы агента по типам, пробелы базы, действия по статусам, переходы на резервную модель, открытые SSE-потоки.
- Лимит: 60 вопросов в минуту на пользователя (`RATE_LIMIT_PER_MIN`), тело ≤ 64 КБ, вопрос ≤ 2000 символов.
- `X-Request-Id` в ответе и логах; тела запросов в логи не пишутся.
- Пользователь — из заголовка `X-Demo-User`. Параметр `?user=` действует только для SSE (`GET /chat/sessions/{id}/events`: `EventSource` не умеет передавать заголовки); на остальных маршрутах он не меняет пользователя.
- Защита от cross-origin запросов: изменяющий запрос (POST, PATCH, PUT, DELETE) с заголовком `Origin`, которого нет в `CORS_ORIGINS`, отклоняется (403), а не только остаётся без CORS-заголовков. GET и запросы без `Origin` (curl, MCP-клиенты, серверные интеграции) не затрагиваются.
- Доступ запрашивается только к ресурсам из белого списка (Jira, GitLab, Grafana, Git). На неизвестный ресурс помощник честно отказывает (без черновика и без внутренней ошибки) и предлагает обратиться к наставнику; наставнику и руководителю — в IT Support.

## Состояние
In-memory хранилище со снимком на диск (`STATE_FILE`): атомарная запись раз в 2 с при изменениях и при остановке. После перезапуска заявки, история, чек-листы и диалоги на месте; недосчитанные ответы помечаются failed.

## Ошибки
`{"error":{"code","message"}}`. Коды: bad_request, unauthorized, forbidden, not_found, conflict, rate_limited, agent_error.

## Roadmap (вне прототипа)
